## 2. 分区调整风险评估

### 2.1 调整方案

```
当前布局:
  ota_0: 0x20000,  0x3F0000 (3.94MB)  ×2
  assets: 0x800000, 8MB

建议布局 (方案 A):
  ota_0: 0x20000,  0x4A0000 (4.63MB)  ×2    ← +696KB/槽
  assets: 0x960000, 0x6A0000 (6.63MB)        ← -1.57MB
```

**精确边界计算**：
- OTA 区域：0x20000 + 2×0x4A0000 = 0x960000
- Assets 区域：0x960000 → 0x1000000 = 0x6A0000 = 6,946,816 B (6.63MB)
- Assets 当前使用 2,790,863 B → 新分区利用率 = **40.2%**（剩余 4.16MB，仍充裕）
- 总计：0x960000 + 0x6A0000 = 0x1000000 = 16MB ✓

### 2.2 风险矩阵

| # | 风险 | 严重度 | 概率 | 影响 | 缓解措施 |
|---|---|---|---|---|---|
| R1 | **OTA 断裂**：旧固件无法 OTA 到新分区布局 | 🔴 高 | 100%（必然） | 用户必须 USB 重新烧录，无法远程升级 | 文档明确标注 v3.0.0 需 USB 烧录；推送通知 |
| R2 | **otadata 错乱**：otadata 指向旧偏移的分区 | 🔴 高 | 高 | 设备启动黑屏/无法引导 | 烧录时执行 `idf.py -p COM4 erase-otadata` 或 `esptool erase_region 0xd000 0x2000` |
| R3 | **Assets 数据丢失**：SPIFFS 偏移变化导致文件系统失效 | 🟡 中 | 100%（必然） | 唤醒词/字体/表情丢失，首次启动需联网下载 | 设备首次启动自动从服务器下载 assets；如有自定义 assets 需备份 |
| R4 | **对齐违规**：分区偏移未按 64KB 对齐 | 🟢 低 | 已排除 | 编译期 check_sizes.py 会报错 | 0x960000 是 0x10000 的整数倍 ✓ |
| R5 | **Assets 余量不足**：未来 assets 增长超过 6.63MB | 🟢 低 | 低 | assets 下载失败 | 当前仅用 2.66MB，6.63MB 足够支撑 2x 增长 |
| R6 | **NVS 数据保留** | 🟢 无 | — | — | NVS 偏移不变（0x9000），WiFi 密码/设置保留 |
| R7 | **烧录命令复杂化**：assets 偏移变化 | 🟡 中 | 中 | `idf.py flash` 需同时烧录分区表 + assets + 擦除 otadata | CMakeLists.txt 自动检测并注册 assets 烧录（已有逻辑） |

### 2.3 风险总结

**整体风险等级：🟡 中等**

- 最大风险是 **R1（OTA 断裂）**——这是**必然发生**的，无法避免。但这是一次性成本（仅 v3.0.0 需 USB 烧录），之后新分区的 OTA 可以正常工作。
- **R2（otadata 错乱）** 可以通过标准烧录流程解决（`erase-otadata`）。
- **R3（Assets 丢失）** 有自动恢复机制（首次启动联网下载）。
- 无数据损坏风险（NVS 保留），无不可逆操作。

### 2.4 建议：何时调整

| 条件 | 建议 |
|---|---|
| 当前（剩余 284KB） | ⏸ **暂不调整**。仍有 5-6 个版本空间 |
| 固件达到 3.8MB（剩余 ~140KB） | ⚠️ **开始准备**。规划 v3.0.0 分区调整 |
| 固件达到 3.9MB（剩余 ~40KB） | 🔴 **必须调整**。否则下个版本无法编译 |

**当前建议**：不调整分区。先通过代码优化控制固件大小增长。在 v2.7.0~v2.8.x 期间规划 v3.0.0 分区调整。

### 2.5 替代方案：不调分区，控制代码大小

| 手段 | 预估节省 | 说明 |
|---|---|---|
| 编译优化 `-Oz`（最小体积） | ~50-100KB | sdkconfig 改 `CONFIG_COMPILER_OPTIMIZATION_SIZE=y`（可能已开） |
| 移除未用板级代码 | ~20-50KB | 条件编译排除非目标板的驱动 |
| 精简日志字符串 | ~10-20KB | Release 模式降低 ESP_LOG 级别 |
| 延迟初始化（Lazy init） | 0（运行时） | 减少静态数据段 |
| LTO 链接时优化 | ~20-40KB | `CONFIG_COMPILER_OPTIMIZATION_ASSERTIONS_LEVEL=n` |

**预估总节省**：100-200KB，可延长 3-4 个版本。

## 6. 结论

1. **分区暂不调整**——当前 284KB 余量足够 5-6 个版本，风险大于收益
2. **优先做 v2.7.0**——HTTP 服务器体验完善（mDNS + 在线播放/查看 + 删除），纯软件不碰分区
3. **监控固件大小**——每次提交检查 `xiaozhi.bin` 大小，达到 3.8MB 时启动 v3.0.0 规划
4. **分区调整风险可控**——主要是 OTA 断裂（一次性成本）+ otadata 清理（标准流程），无数据丢失风险
